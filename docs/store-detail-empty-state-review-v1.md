# store-detail-empty-state-review-v1

対象: `/stores/[id]` 店舗詳細「0品を掲載しています」問題の調査（設計レビューのみ・実装なし）

## 総合判定

「○品を掲載しています」が **文字通り0と表示されるケースは、現在のコードと本番データでは再現できなかった**。コードロジック上、`/stores/[id]` で到達可能な店舗は常に `displayFoods.length >= 1` になる構造であり、Codex報告の「0品を掲載しています」はi18n Phase 2D-D実装が原因ではない（後述の通り独立に再確認済み）。

一方、調査の過程で **別の重大な既存バグ**（店舗IDの衝突により、`/stores` 一覧の複数の異なる店舗カードが、無関係な1つの店舗詳細ページに誤って遷移する）を発見した。これは「0品」報告そのものではないが、店舗詳細ページの信頼性・コレクション体験を損なう、優先度の高い別問題として扱うべき。

## 発生している問題

### 1. 「0品を掲載しています」: 再現できず

- `lib/store-utils.ts` の `buildStoresFromFoods()` は、`listFoods()`（公開フィルタ済みフード一覧）を入力に、各フードが参照する店舗ごとに `StoreWithFoods` を構築する。店舗オブジェクトは「最低1件のフードが存在するときだけ」生成される（`storeMap.set(storeKey, { ..., foods: nextFoods, ... })` は必ず1件以上の `food` をトリガーに実行される）。
- `getStoreDisplayFoods(foods, store)` は重複排除のみを行う関数で、フィルタは行わない。入力 `foods.length >= 1` であれば、`foodMap` のサイズは最低1になる（重複排除で減ることはあっても0にはならない）。
- `app/stores/[id]/page.tsx` の `displayFoods = getStoreDisplayFoods(store.foods, store)` は、`store` が `findStoreById(stores, id)` で見つかった時点で `store.foods.length >= 1` が保証されている。
- 本番サンプリング（`shop-1tt48e8`=3品、`shop-1b3f2nw`=1品、`shop-56paaa`=4品、`shop-102yaa2`=3品）でも0件は確認されなかった。

→ 現在のコードパス上、`/stores` 経由で到達する `/stores/[id]` で「0品を掲載しています」が出ることは構造的に想定できない。

### 2. 新たに発見: 店舗IDの衝突によるリスト/詳細の不一致（重大）

`/stores` 一覧を確認したところ、以下の異なる店舗カード（名前・エリア・代表商品がすべて異なる）が、すべて同じURL `/stores/shop-1tt48e8` にリンクされている:

- ボードウォーク・スナック（アミティ・ビレッジ）
- ワーフカフェ（サンフランシスコ・エリア）
- ディスカバリー・レストラン（ジュラシック・パーク）
- シネマ 4-D 前フードカート（ハリウッド・エリア）
- スヌーピー・バックロット・カフェ / ハローキティのコーナーカフェ（ユニバーサル・ワンダーランド）
- イーブル・イーツ（ミニオン・パーク）

しかし `/stores/shop-1tt48e8` を実際に開くと、これらのいずれとも無関係な **「アミティ・アイスクリーム」（アミティ・ビレッジ、3品）** が表示される。さらに `/stores/shop-102yaa2`（アミティ・アイスクリームの正規カードのリンク先）も同じ「アミティ・アイスクリーム」を表示する。

つまり `shop-1tt48e8` というIDが、最低でも7つの異なる店舗グループに「代表ID」として割り当てられているが、実際に解決されるのは1店舗だけで、残りの6件は「自分のカードをクリックすると無関係な他店舗の詳細ページに飛ぶ」状態になっている。

## 原因候補

`buildStoresFromFoods()` の店舗ID決定ロジックに起因すると考えられる。

```ts
const storeKey = buildStoreIdentityKey(candidate.name, candidate.areaName); // 店舗名+エリア名で一意
...
const selectedId = current && !current.officialUrl && officialUrl ? candidate.id : current?.id ?? candidate.id;
```

- `storeMap` のキー（`storeKey`）は「店舗名＋エリア名」で一意化されており、これは正しく機能している（一覧に63件の異なるカードが出ている）。
- しかし各店舗の `id` フィールド（`selectedId`）は `candidate.id`（= `food.shop.id` または `${food.areaId}-${normalizeShopName(location.shopName)}`）から決まり、**`storeKey` をまたいで一意であることは保証されていない**。
- 上流データ（生成JSON/Supabase）側で、複数の無関係な店舗の `food.shop.id` が同じ値（例: `"1tt48e8"`）になっている可能性が高い。その場合、`storeMap` には7つの異なる `StoreWithFoods`（storeKeyはすべて別）が存在するが、そのうち少なくとも6つの `id` が `"shop-1tt48e8"` という同じ値になり、`findStoreById()` の `.find()` は配列内で最初に一致した1件しか返せない。
- `generateStaticParams()` も同じ `stores` 配列から `id`/`aliases` を集めているため、重複した `id` に対して複数の静的ページが生成されようとし、ビルド上は1ページに収束する（＝そのうち6店舗分のリンクは「別の店舗の詳細」に着地する）。

## i18n起因かどうか

**起因しない。** 今回、`app/stores/[id]/page.tsx`（Phase 2D-D実装後の現状）と `lib/store-utils.ts` を改めて全文確認したが、`displayFoods` の算出 (`getStoreDisplayFoods(store.foods, store)`) ・店舗解決 (`findStoreById`) ・店舗構築 (`buildStoresFromFoods`) のロジックはPhase 2D-Dで一切変更されていない。Phase 2D-Dは `{displayFoods.length}品を掲載しています。` という文字列を `<I18nText k="store.availableFoodsCount" params={{ count: displayFoods.length }} />` に置き換えただけで、`count` の値の計算方法・タイミングは変わっていない。`design-review-i18n-phase2d-d.md` の結論（pre-existingかつi18n非起因）を、今回の独立コードリードでも再確認できた。

また、発見した「店舗ID衝突」問題も、`buildStoresFromFoods`・`generateStaticParams` のロジックであり、Phase 2D-D（`/stores/[id]` のテキスト国際化のみ）の変更範囲外。

## データ起因かどうか

- 「0品を掲載しています」自体: 現状では再現不可のため「データ起因」と断定できない。将来的に `listFoods()` がさらに厳しくなる/store構築ロジックが変わるなどでstore.foodsが空になり得る変更が入った場合のみ問題化する、潜在リスク。
- 「店舗ID衝突」: **データ起因の可能性が高い**。上流の `food.shop.id` の値が、複数の異なる実店舗にわたって再利用されている（生成データの店舗ID付与ロジックの問題、または元データソース側のID欠落・フォールバック値の衝突）と推測される。ただし「推測で判断しない」の方針に従い、これは `lib/repositories/generated-data.ts` や生成元JSONの実データを確認しないと確定できない（今回のスコープでは未確認）。

## UI/UX起因かどうか

- 現在のワーディング「{{count}}品を掲載しています。」自体は、count >= 1 の現状運用では自然。
- ただし `count === 0` が将来発生した場合、`StoreFoodList` 側の空状態メッセージ（`t("store.availableFoodsEmpty")`）と「0品を掲載しています。」が画面上に**二重に表示される**構成になっており、これは仕様として未整理（防御的には「0件のときはカウント行自体を非表示にする」べき）。
- 「店舗ID衝突」問題は、UXとしては「コレクション欲」「ゲーム感」を大きく損なう（自分の好きな店舗のカードをタップしたのに、別の店舗ページが開く）。ユニコレの最重要目的（ユニバ感・コレクション欲）に対する影響度は、テキスト翻訳の話より大きい。

## 直すべき優先度

| 項目 | 優先度 | 理由 |
|---|---|---|
| 店舗ID衝突によるリスト/詳細不一致 | **高** | 63店舗中、確認できただけで7店舗（うち6店舗が誤遷移）。ユーザーが正しい店舗ページに到達できない。コレクション体験の信頼性に直結。 |
| 「0品」表示の防御的UI（count===0時にカウント行を非表示） | 低 | 現状は到達不能だが、将来の変更に対する保険として軽微な条件分岐を入れる価値はある。 |
| i18n Phase 2D-D | 対応不要 | 今回の問題と無関係。承認済みのまま。 |

## 修正案（設計レベル・未実装）

### A. 店舗ID衝突（高優先度）— 別トラックの調査が必要

実装方針の選択肢（いずれも本ドキュメントでは決定しない、次の調査ステップで検討）:

1. `selectedId` の決定時に `storeKey`（店舗名+エリア名）由来のフォールバックIDを組み込み、`candidate.id` が他の `storeKey` グループと衝突する場合は `storeKey` ベースのIDを採用する。
2. `buildStoresFromFoods()` の戻り値に対して、`id`/`aliases` の重複を検出する整合性チェック（開発時アサーションやログ）を追加し、今後同種の衝突を早期発見できるようにする。
3. 上流データ（生成JSON）側で `shop.id` の付与ロジックを見直す（根本対応だが影響範囲が大きい）。

→ いずれも `lib/store-utils.ts` のID生成ロジックとデータ生成パイプラインに関わるため、i18nより大きい変更。**実装前に棚卸し（衝突件数の全件調査）を行う調査限定の/goalを別途作るべき**。

### B. 「0品」時の表示防御（低優先度）

`app/stores/[id]/page.tsx` の該当ブロックを、`displayFoods.length > 0` のときだけ「○品を掲載しています」行を表示するように条件分岐する（`store.availableFoodsCount` キー自体は変更不要）。`StoreFoodList` の空状態メッセージのみで成立させる。影響範囲はこの1ファイルのみで、軽量。

## Codex実装前に確認すべき質問

1. Codexが「0品を掲載しています」を観測したと報告した、具体的な `/stores/[id]` のURL（店舗ID）は何か。再現手順を提示してほしい。
2. その観測は、本当に「○品を掲載しています」の数字部分が `0` だったのか、それとも `StoreFoodList` の空状態メッセージ（「該当する商品が見つかりませんでした」等）が表示されていたのを「0品」と表現しただけなのか。
3. Codexは巡回時に、`/stores` 一覧のカードリンクと `/stores/[id]` の表示内容が一致しているかを確認したか。今回発見した `shop-1tt48e8` のような「複数カードが同じURLに着地し、無関係な店舗が表示される」ケースを他に何件確認できるか（全件棚卸し）。
4. 上流の生成データ（`lib/repositories/generated-data.ts` が読むJSON）で、`shop.id` が複数の異なる店舗名にわたって重複している件数はどの程度か。

## 推奨する次の/goal方針（まだ作成しない）

- 今回の「0品を掲載しています」報告は、現状のコード・本番データでは再現できず、i18n Phase 2D-Dの承認判断（承認済み）に影響しない。このテーマでの追加/goalは不要。
- 一方で発見した「店舗ID衝突によるリスト/詳細不一致」は、i18nシリーズとは独立した、データ整合性に関する重大な別トラック課題。次の/goalは**実装ではなく調査専用**とし、「`/stores` 一覧の全63件について、カードのリンク先と詳細ページの表示内容が一致するかを棚卸しし、衝突件数と該当ペアをレポートする」ことを目的とするべき。修正方針（A案/A2案/A3案）は、その棚卸し結果を見てから設計する。
- 「0品」防御的UI（B案）は、上記調査と並行して、低優先度の単独/goalとして別途出すことは可能（任意）。
