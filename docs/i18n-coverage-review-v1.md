# i18n-coverage-review-v1.md

担当: Claude（PO/UX/UIデザイン/レビュー）
目的: i18n Phase 2着手前の翻訳漏れ監査。現在の翻訳済み範囲と、未翻訳のまま残っているUI文言を全体洗い出しし、Phase 2の対象範囲を決める。
方法: `lib/i18n/dictionaries.ts` の既存キーと、対象ページ・コンポーネントのソースコードを直接読み、ハードコードされた日本語文言を抽出して比較。
対象言語: ja / en / ko / zh-TW
重要な前提: 商品名・店舗名・エリア名・カテゴリ名などデータ由来の固有名詞は今回も翻訳対象外。「店舗」「エリア」「販売中」「限定」「販売終了」などのUIラベルは翻訳対象。

---

## 総合判定

**Phase 1で翻訳されたのはnav・footer・settings（言語切替を含む）のみで、UI全体で見るとごく一部。** ホーム、フード一覧/詳細、食べた記録、エリア一覧/詳細、店舗一覧/詳細のメイン領域はほぼ全て日本語ハードコードのまま残っている。

加えて、Phase 1で `lib/i18n/dictionaries.ts` に追加された `common.*`（`saleActive` / `limited` / `ended` / `eaten` / `area` / `store` / `home` / `viewAll` / `price` / `registeredCollection` / `search`）は**どのコンポーネントからも参照されていない「未使用キー」**であることを確認した。Phase 2はこの`common.*`を実際に配線することを軸に、再利用頻度の高いUIラベルから着手するのが効率的。

Phase 2は「全ページ一括翻訳」ではなく、**再利用頻度が高い共通ラベル（ステータス系・ナビゲーション系の単語）から段階的に**進めることを推奨する。食べたレビュー（ユーザー投稿コンテンツ）・admin系・フィルター用カテゴリ名は今回は対象外とすることを推奨する。

## Phase 2で翻訳すべき範囲（推奨）

優先度順:

1. **ステータス・状態ラベルの一元化**: `common.*` に既存のキー（saleActive/limited/ended/eaten/area/store/price/viewAll/search/registeredCollection/home）を実際に配線する。具体的には `lib/constants.ts` の `statusLabels`/`shopTypeLabels`、`food-card.tsx`、`food-detail.tsx`、`area-*`系コンポーネントの「販売中/限定/販売終了/食べた/食べた済み/エリア/店舗/価格/すべて見る」など、複数ページで繰り返し使われている短いラベルから翻訳キー化する。再利用率が高く、翻訳済みキーの実利用が一気に進むため最も効率的。
2. **ホーム（`/`）のメインUIラベル**: 「今集められるフード」「期間限定コレクション」「エリア一覧」「店舗から探す」「登録済みコレクションを見る」など、訪問者が最初に見る画面のため優先度高。
3. **共通の絞り込み・ソートUI（`/foods`, `/eaten`）の主要ラベル**: 全エリア/全ジャンル/全店舗/価格安い順・高い順/新しい順など、UIラベルとして明確なもの。
4. **エリア詳細・店舗詳細のセクション見出し**: まず食べたい3品/終了間近のフード/残りのフード/販売場所/営業時間/公式サイト/店舗情報など。
5. **設定ページのデータ管理セクション**（`local-data-backup-panel.tsx`）: バックアップ出力/復元/全データ削除と関連メッセージ。

## Phase 2ではまだ触らない方がいい範囲

- **admin系（`app/admin/*`, `components/admin-catalog-manager.tsx`）**: 内部管理ツール。ユーザー向け多言語対応の対象外とすべき。
- **`components/food-reviews.tsx` のユーザー投稿コンテンツ（コメント本文）**: UI見出しと混在しているため、UIラベルだけを切り出す設計判断が必要。コメント自体の自動翻訳は前回のOwner決定（外部翻訳API不使用）により対象外。
- **`/foods` の細かいジャンル・食べ物カテゴリ名（あまい/ちゅろす/ぽっぷこーん等）**: データ分類由来かUI文言かの切り分けが必要。Phase 2の初期スコープからは外し、別途調査が望ましい。
- **`/eaten` の長文説明（コンプ率算出ロジックの説明文など）**: 文量が多く翻訳コストが高い割に利用頻度は低いセクションのため、Phase 2後半または Phase 3 に後ろ倒しを推奨。
- **`Intl.DateTimeFormat("ja-JP", ...)` による日付フォーマット**: ロケール別の日付表示形式に踏み込むと影響範囲が広い。Phase 2では日付表示形式の変更は行わない（文言キーの翻訳のみ）。

## まとめ

Phase 1はnav/footer/settingsという「枠組み」の翻訳に留まり、ユーザーが実際に時間を過ごすホーム・フード一覧/詳細・食べた記録・エリア/店舗詳細はほぼ未翻訳。`common.*`の既存キーが未使用である点も含め、Phase 2はまず「再利用頻度の高い共通ラベルの配線」から着手し、その後ページ単位で段階展開するのが妥当。admin系・ユーザー投稿コンテンツ・データ分類名は今回のスコープ外として明確に切り分けることを推奨する。

本ドキュメントは監査・設計用であり、Codex用 `/goal` はまだ作成していない。
