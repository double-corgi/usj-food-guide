## 0. スコープと不変条件

今回のスコープは「2026年夏限定メニューの登録・特集・進捗表示」と「季節を問わず使い回せる季節コレクション基盤」の設計。

変更してはいけないもの:

- Bundle ID、Capacitor appId、AdMob、Supabase本番設定、Apple Developer設定
- 既存の食べた記録（localStorage / Supabase同期の `UserFoodLog`、キーは `foodId`）。既存foodのidは変更・削除しない
- 公開ルール「通常画面は `review_status='approved'` かつ `hidden=false` のみ表示」
- 表記: 日本語「ユニコレ」、英字「UNICOLLE」。Lが1つ少ない誤表記は禁止
- 非公式アプリであることの明示（UnofficialNotice）。公式アプリと誤認させるデザイン・公式イベントロゴの模倣は禁止

## 1. 現在の問題点

調査対象: `components/home-dashboard.tsx`, `home-progress-client.tsx`, `food-grid.tsx`, `food-detail.tsx`, `eaten-experience.tsx`, `app/admin/*`, `supabase/schema.sql`, `types/domain.ts`, `screenshots/*`。

1. **季節特集がキーワード推測で成立している。** ホームの限定コレクションは `LIMITED_WORDS`（"夏"、"ハロウィーン" など商品名の文字列一致）で抽出しており、商品名に季節語が含まれない夏限定商品は特集から漏れる。逆に通年商品が誤って混入しうる。「不明な情報を推測で確定しない」方針に反する。
2. **「新着」がユーザーに見えない。** ソートに `new` はあるが、ホームにも一覧フィルターにも「最近追加・更新」の明示的な導線がない。`created_at` はcrawl時刻で公開時刻と一致しない。
3. **価格バリエーションの受け皿がない。** `price` / `priceMin` / `priceMax` / `priceNote` のみで、「単品¥600 / カップ付き¥1,400」を構造化できない。運用上、カップ付きを別foodとして登録して重複が生まれる温床になっている。
4. **重複防止が登録後の後追い。** `unique(shop_id, normalized_name)` と `canonical_group_id` はあるが、管理画面に「登録前の類似チェック」「重複候補キュー」のUIがなく、店舗違い・表記揺れ・価格違いの重複は人手発見に依存している。
5. **管理画面に編集ワークフローの状態がない。** `review_status` は pending/approved/rejected のみで「下書き（情報収集中で公開したくない）」を表現できない。画像未確認・価格未確認・情報確認日の鮮度を横断で見るキューもない（/admin/prices はあるが分散している）。
6. **ホームのセクション間で商品が重複しうる。** アクティブコレクション棚・限定コレクション・最近の記録が同じ商品を重ねて表示できてしまう。DESIGN.md の「商品候補を同じ画面内で何度も重複表示しない」に反する。
7. **販売期間・情報確認日の表示が弱い。** 詳細では表示されるが、「情報確認日」がカードや詳細で目立たず、期間限定商品の「いつまで買えるか」が一覧から読み取りづらい。
8. **食べた記録に季節の切り口がない。** エリア別・ジャンル別進捗はあるが、「2026夏限定を何個食べたか / 総数 / 使った金額」を見る場所がない。25thコレクションはハードコード的で、ハロウィーン・クリスマスに使い回せない。
9. **デザイン基準の不整合。** DESIGN.md / USJ_FOOD_GUIDE_DESIGN.md は緑をCTA主色とするが、現行ホーム・フード一覧・App Storeスクリーンショットは紺・青・金のブランドに移行済み。文書と実装が乖離しており、Codexが旧基準の緑で実装する事故が起きうる（eaten画面の旧緑スクリーンショットが乖離の実例）。
10. **旧ブランド表記の残存リスク。** 過去スクリーンショットに「ユニバフードガイド」表記・緑ロゴが残る。App Store提出物は現行「ユニコレ」紺金ブランドで撮り直しが必要。

## 2. 残すべき良い部分

1. 写真主役の2カラム図鑑グリッド。画像比率統一・価格と「食べた」ボタンの位置揃えは維持する。
2. 紺・金・青のホームヒーロー（コレクション進捗 0/183 の見せ方）。ブランドの核として維持。
3. `canonical_group_id` / `duplicateGroupId` / `dedupeFoodsByCanonical` による正規化基盤。食べた判定が `getCanonicalFoodKey` 経由で吸収される設計は優秀で、重複マージ時に記録を壊さない。今回はこの上に積む。
4. `food_locations` による複数店舗展開の表現。店舗違いを別foodにしない方針はそのまま強化。
5. `source_url` / `last_checked_at` 必須のデータ規律。公式参照元を持たない商品を作れない構造。
6. 下部ナビ5タブ（ホーム / 探す / 食べた / エリア / 店舗）、44px以上のタップ領域、細ゲージの進捗表現。
7. 食べた記録のlocalStorage保存・エリア別ゲージ・アルバム表示。
8. 非公式表記・免責の徹底（UnofficialNotice、/disclaimer）。
9. カテゴリチップの横スクロールと「表示条件」折りたたみ。フィルターを一覧の一等地から遠ざける構成。

## 3. デザイントークン（全画面共通・今回の基準）

DESIGN.md の余白・タイポ基準は維持しつつ、色は現行ブランドに合わせて本書を正とする。

### 3.1 カラー

| トークン | 値 | 用途 |
|---|---|---|
| `--base` | `#fffaf5`（クリーム） | 画面背景 |
| `--surface` | `#ffffff`（白） | カード・シート |
| `--ink` | `#0f172a` | 本文 |
| `--sub` | `#64748b` | 補足文字 |
| `--navy` | `#10233f`（紺） | 見出し強調・主CTA背景 |
| `--brand-blue` | `#1d4ed8`（青） | 価格・リンク・進捗ゲージ |
| `--gold` | `#f7b267`（金） | コレクション演出・限定バッジ |
| `--season-accent` | 季節ごとに定義。2026夏は `#38b6c9`（水色） | 季節特集の帯・チップ・ゲージのみ |
| `--alert` | `#f43f5e` | 販売終了間近・エラーのみ |

ルール:

- 水色（`--season-accent`）を使ってよいのは「夏限定」を表す要素のみ: 特集セクションの見出しアクセント、`夏限定` チップ、夏進捗ゲージ、フィルターのONステート。面積の大きい背景には使わない（使うなら10%以下のtint `#e8f7fa`）。
- 主CTA（食べたボタン等）は紺で全画面統一。緑（park green）は新規実装で使用しない。既存の緑が残る画面はこの機会に紺系へ揃える。
- 公式2026夏イベントのキービジュアル・ロゴ・フォントを模倣しない。季節表現は「水色 + 文言」だけで行い、イラスト装飾を足さない。

### 3.2 タイポグラフィ・余白

DESIGN.md どおり: Page title 28px / Section title 20px / Card title 15px（2行固定枠）/ Body 14-15px lh1.6+ / Caption 11-12px。最小フォント11px、最小タップ領域44px。余白スケール 4/8/12/16/24/32px、セクション間32px。iPhone SE (375px) で2カラムカードが崩れないこと。

### 3.3 共通コンポーネント（新規・変更）

- **SeasonChip**: 高さ22px、角丸11px、`bg #e8f7fa / text #0e7490 / border #38b6c9(40%)`、文言「夏限定」「〜8/31まで」。1カードに載せるバッジは最大2（例: 夏限定 + NEW）。
- **NewBadge**: 「NEW」金色 `--gold` 背景・紺文字。`published_at` から14日以内のみ表示。
- **PriceBlock**: 既定価格を `¥1,800` 20px黒太字・青。バリエーションがある場合は下に12pxで「全2種 ¥600〜¥1,400」。カードでは「¥600〜」+「2種」チップ。
- **InfoFreshness**: 「情報確認日 2026/7/1・公式サイト↗」12px `--sub`。30日超過で「情報が古い可能性があります」を同じ行に `--alert` ではなく `--sub` の警告アイコン付きで表示（一般画面は騒がせない）。
- **SeasonProgressCard**: 細ゲージ6px、`--season-accent`。「2026夏コレクション 3/12・¥2,450」。

## 4. データ設計（必要なデータ項目）

### 4.1 新規テーブル: collections（季節コレクション基盤）

ハロウィーン・クリスマスにそのまま使い回すための一般化。キーワード抽出は廃止し、管理画面での明示付与に置き換える。

```sql
create table if not exists public.collections (
  id text primary key,                -- 'summer-2026', 'halloween-2026'
  name text not null,                 -- '2026 サマーコレクション'
  season_type text not null check (season_type in
    ('summer','halloween','christmas','easter','anniversary','event','other')),
  starts_on date,
  ends_on date,
  accent_color text,                  -- '#38b6c9'。nullは--gold扱い
  is_featured boolean not null default false,  -- ホーム特集に出すか
  sort_order integer not null default 100,
  created_at timestamptz not null default now()
);
alter table public.foods add column if not exists collection_id text
  references public.collections(id) on delete set null;
```

- 1商品につき所属コレクションは0または1（複雑化させない）。
- ホーム特集・夏フィルター・季節進捗はすべて `collection_id = 'summer-2026'` を条件にする。**商品名の文字列一致による季節判定コード（LIMITED_WORDS依存の buildLimitedCollection）は特集抽出から撤去**（限定バッジ表示のフォールバックとしてのみ残してよい）。
- 25th既存特集は `anniversary` コレクションとしてデータ移行し、同じUIで表示。

### 4.2 新規テーブル: food_variants（価格バリエーション）

```sql
create table if not exists public.food_variants (
  id text primary key default ('var-' || replace(gen_random_uuid()::text,'-','')),
  food_id text not null references public.foods(id) on delete cascade,
  label text not null,                -- '単品', 'カップ付き', 'レギュラー', 'ラージ'
  price integer,
  is_default boolean not null default false,
  sort_order integer not null default 100,
  source_url text,
  last_checked_at timestamptz,
  unique (food_id, label)
);
```

- ルール: **価格・容器・サイズ違いは food_variants で表現し、新しいfoodを作らない。**
- `foods.price` は default variant の価格と常に一致させる（管理画面保存時に同期）。`price_min` / `price_max` はvariantsから導出。
- variantが1件（単品のみ）の場合、UIはバリエーション表示を出さない。

### 4.3 foods 追加カラム

```sql
alter table public.foods add column if not exists published_at timestamptz;      -- 公開日時（新着判定の唯一の基準）
alter table public.foods
  drop constraint if exists foods_review_status_check,
  add constraint foods_review_status_check
  check (review_status in ('draft','pending','approved','rejected'));
```

- `published_at`: review_statusを初めて `approved` にした時刻を保存。**新着 = `published_at` が14日以内**。crawl時刻 `created_at` は新着判定に使わない。
- `draft`: 下書き。通常画面に出ない（公開条件は従来どおり approved && !hidden なので追加の除外実装は不要）。

### 4.4 夏限定メニュー1商品が持つ項目（登録チェックリスト）

| 項目 | 格納先 | 必須 |
|---|---|---|
| 商品画像 | `food_images`（imageVerified承認後に表示） | 公開時必須 |
| 商品名 | `foods.name` / `normalized_name` | 必須 |
| 商品説明 | `foods.description`（80字以内目安） | 任意 |
| 価格（既定） | `foods.price` = default variant | 公開時必須 |
| 価格バリエーション | `food_variants` | 2種以上ある場合必須 |
| 販売店舗 | `foods.shop_id` + 複数店舗は `food_locations` | 必須 |
| エリア | `foods.area_id`（shop経由と整合必須） | 必須 |
| カテゴリ | `foods.category` | 必須 |
| 販売開始日 | `foods.start_date` | 判明時のみ（推測禁止） |
| 販売終了日 | `foods.end_date` | 判明時のみ（推測禁止） |
| 期間限定表示 | `foods.is_limited=true` + `collection_id='summer-2026'` | 必須 |
| 情報確認日 | `foods.last_checked_at` | 必須 |
| 公式参照元 | `foods.source_url`（公式URL） | 必須 |
| 食べた記録 | 既存 `UserFoodLog`（変更なし） | — |

販売終了日が未発表の場合は `end_date=null` とし、UI表示は「販売期間: 2026/7/1〜（終了日未発表）」。勝手に「8/31まで」と書かない。

## 5. 新しいホーム構成

目的: 開いて3秒で「夏の新作がある」「自分の進捗」がわかる。セクション順と重複排除を固定する。

```
1. ヒーロー（既存維持・高さ圧縮）
   - ブランドマーク + コレクション進捗 n/N + 細ゲージ
   - 非公式表記1行（既存 UnofficialNotice 位置維持）
2. ★新規★ 2026夏限定特集（is_featured=true の collection を自動表示）
3. ★新規★ 最近追加・更新されたフード
4. 食べた進捗サマリー（既存を1カードに圧縮）
5. エリア別進捗（既存維持）
6. 店舗一覧導線 / 全フード導線 / リクエスト導線（既存維持）
```

### 5.1 夏限定特集セクション

- 見出し: 左に4px幅×20pxの水色バー +「2026 サマーコレクション」20px紺。右に「すべて見る →」（`/foods?collection=summer-2026`）。
- 見出し直下に SeasonProgressCard:「食べた 3/12 ・ ¥2,450」細ゲージ水色。0/12でも表示。
- 横スクロールレール: カード幅168px（画面の約43%で「次がある」ことを見せる）、画像正方形、商品名2行固定、価格、SeasonChip。表示は最大10件 + 末尾「すべて見る」タイル。
- 並び: published_at 降順。販売終了品は特集レールに出さない（一覧側で見られる）。
- collectionが存在しない期間（季節の谷間）はセクションごと非表示。ホームは空白を残さない。
- 掲出条件は `collection_id` のみ。名前推測での混入禁止。

### 5.2 最近追加・更新セクション

- 見出し「最近追加されたフード」+「すべて見る →」（`/foods?filter=new`）。
- 横レール最大8件。カードは特集と同型 + NewBadge。
- **重複排除ルール（このホームの核）**: 同一 canonical key の商品は、ホーム内で1回しか商品カードとして出さない。優先順位は「夏限定特集 > 最近追加 > その他レール」。夏特集に出た商品は最近追加レールから除外する。集計系（進捗ゲージ・エリア進捗）は対象外。
- 除外の結果0件になったらセクション非表示。

### 5.3 食べた進捗サマリー

- 1カードに「販売中コンプ率」「食べた数」「夏コレクション進捗」を横3分割で表示（数字20px・ラベル11px・ゲージ4px）。タップで `/eaten`。大きな統計カードを縦に積まない。

## 6. フード一覧の構成

### 6.1 フィルター体系

カテゴリチップ行（既存）の直後に**クイックフィルター行**を新設。ここが今回の主改善。

```
[☀ 夏限定] [NEW 新着] [販売中] [未食] …横スクロール
```

- 夏限定チップ: `collection_id='summer-2026'`。ON時は水色ステート。URLは `?collection=summer-2026`（今後 `halloween-2026` 等も同じパラメータ）。
- 新着チップ: published_at 14日以内。`?filter=new`。
- 販売中 / 販売終了: 既存 saleFilter を露出（既定は販売中）。販売終了ONのとき、カード画像に「販売終了」グレーオーバーレイ35% + ラベル。
- 未食 / 食べた: 既存modeを一覧内トグルに昇格。
- 「表示条件」折りたたみ内は既存どおり: エリア、店舗、店舗タイプ、提供形態、価格有無、画像有無、並び順。並び順に「新着順（published_at desc）」を追加し、`new` ソートの基準を published_at に変更。
- 複数フィルターはAND。適用中フィルター数を「表示条件 (2)」のようにバッジ表示。0件時は「条件に合うフードがありません」+「条件をリセット」ボタン。

### 6.2 カード仕様（変更点のみ）

- 一覧は常に `dedupeFoodsByCanonical` 済み（既存維持）。同一商品が2枚出たらバグ。
- バッジ最大2: 優先順位「販売終了 > 夏限定 > NEW > 販売終了間近」。3つ目以降は捨てる。
- 価格: variantsが複数ある場合「¥600〜」+ 右に11px「2種」チップ。価格未確定は「価格未確認」12px `--sub`（画像上には載せない）。
- 店舗・エリア: エリア名1行（既存）。カード内に店舗名は出さない（DESIGN.md維持）— 店舗はフィルターと詳細で扱う。
- 画像・名前・価格・店舗の一致保証はデータ側（§9.3 公開ゲート）で担保し、カードは food 1件のフィールドのみから描画する（別foodの値を合成表示するコードを書かない）。

## 7. 商品詳細の構成

上から順に（DESIGN.md の順序を維持しつつバリエーション行を追加）:

```
1. 代表画像（h300/sm540 既存）
   - 画像上バッジ: 図鑑No / 販売終了 / 夏限定（SeasonChip）最大3種→実表示は2まで
2. 商品名（22px 2行可）+ カテゴリ・エリアのテキストリンク
3. PriceBlock
   - 既定価格 ¥600
   - ★新規★ バリエーション表: 行ごとに「ラベル / 価格」
     例)  単品          ¥600
          カップ付き    ¥1,400   ← is_default に「基準」11pxラベル
   - 枠線1px #e5e7eb の薄いテーブル。2件以下ならテーブルでなく2行表示
4. 販売期間・状態
   - 「7/1(水)〜8/31(月) 期間限定」/ 終了日未発表なら「〜終了日未発表」
   - 残り14日以下: 「あと n 日」を --alert 12px
5. 販売店舗（food_locations 全件。店舗名 → 店舗ページ、エリア名 → エリアページ）
6. 商品説明（description。3行超は「もっと見る」で折りたたみ）
7. 食べたボタン（紺・幅100%・高さ52px・既存トグル挙動 / 金額入力は既存踏襲。
   variantsがある場合、金額入力の初期候補にvariant価格をチップ表示して選択可能に）
8. レビュー（既存）
9. InfoFreshness（情報確認日 + 公式参照元リンク）+ 非公式注記
10. 修正報告フォーム（既存）
11. 関連商品（既存。同一コレクション優先に変更: sameEvent → collection_id 一致）
```

受け入れの肝: 画像・商品名・価格・店舗はすべて同一 `food.id` のレコード由来であること。canonical代表選択（chooseCanonicalRepresentative）で表示レコードを1つに固定し、他レコードの価格を混ぜない。

## 8. 食べた記録の構成

```
1. サマリーカード（既存2段を維持: 販売中コンプ率 / 図鑑コンプ率 / 食べた数 / 総消費金額）
2. ★新規★ 季節コレクション進捗
   - collections を新しい順に1行ずつ:
     「2026 サマーコレクション  3 / 12   ¥2,450」 + 細ゲージ（accent_color）
     「25thアニバーサリー      8 / 20   ¥9,100」 + 細ゲージ（金）
   - 合計金額 = 該当コレクション商品の UserFoodLog.spentAmount 合計。
     spentAmount未入力の記録は金額に含めず、「¥2,450（金額未入力 1件）」と注記
   - 行タップで /foods?collection=...&mode=eaten
   - 終了したコレクションも残す（アルバムとしての価値）。0/nの過去コレクションは折りたたみ
3. 最近食べたアルバム（既存）
4. エリア別進捗（既存ゲージ）
5. ジャンル別進捗(既存)
```

- 夏限定で食べた数 / 総数 / 合計金額はこの画面とホームサマリー、特集セクションの3か所で同じ計算関数を共有する（`lib/collection-progress.ts` を新設し一元化。二重実装禁止）。
- 分母は「該当collectionの公開商品（approved && !hidden）」。dedupe後のcanonical数。

## 9. 管理画面の構成

### 9.1 ダッシュボード（/admin）

上部にステータスタブ + 件数バッジ:

```
[下書き 4] [確認待ち 7] [公開中 183] [販売終了 22]
```

- 下書き: `review_status='draft'`
- 確認待ち: `review_status='pending'`
- 公開中: `approved && !hidden && saleStatus != ended`
- 販売終了: `approved && saleStatus == ended`

その下に**作業キュー**（件数0でも行を出し、0件は「なし」）:

```
⚠ 画像未確認   n件   → 一覧へ
⚠ 価格未確認   n件   → 一覧へ
⚠ 重複候補     n件   → レビューへ
⚠ 情報が30日以上未確認  n件 → 一覧へ
```

- 画像未確認: 有効画像0件、または `image_verified=false` の画像のみ
- 価格未確認: `price is null` または `price_last_checked_at` が90日超
- 重複候補: §9.3 の検出クエリ結果で未処理のもの
- 30日以上未確認: `last_checked_at < now()-30d` かつ公開中

### 9.2 商品編集フォーム（/admin/foods/[id]・/new）

- 必須欄: 商品名 / カテゴリ / 店舗 / エリア（店舗から自動設定・不一致時エラー）/ 公式参照URL / 情報確認日（保存時に「今日にする」ボタン）
- コレクション: セレクト（なし / 2026夏 / 25th / …）。collections はadminでCRUD可能（id, 名前, 期間, accent_color, is_featured）
- 価格バリエーション: 行追加UI（ラベル・価格・既定ラジオ）。既定行の価格を foods.price に自動同期
- 販売期間: 開始日・終了日。終了日未発表チェックボックス（end_date=null を明示）
- 保存アクション: 「下書き保存」「確認待ちへ」「公開」。公開ボタンは §9.4 公開ゲートを通過しないと押せない（未達項目を赤リストで表示）

### 9.3 重複候補レビュー（/admin/review-center 内に統合）

検出（保存時 + 日次バッチ）:

1. `normalized_name` 完全一致 × 店舗違い → 「store違い重複」候補
2. `normalized_name` 完全一致 × 価格違い → 「variant化」候補
3. trigram類似度 0.85以上（`pg_trgm`、全角半角・記号・長音・スペース正規化後） → 「表記揺れ」候補

レビュー行UI: 左右に2商品（画像・名前・店舗・価格・参照URL）+ アクション3択:

- 「同一商品としてマージ」→ 古い方のfoodをcanonicalにし、新しい方へ `canonical_group_id` 付与 + `hidden=true`。**food行の削除はしない**（食べた記録保護。既存の getCanonicalFoodKey 吸収を利用）
- 「バリエーションに変換」→ 片方を food_variants 行へ移し、food は上記マージと同じ扱い
- 「別商品」→ ペアを dismissed として記録し再提示しない（`duplicate_dismissals(food_id_a, food_id_b)` 小テーブル追加）

新規登録フォームでは、名前入力時に類似候補をインラインで即時表示し「登録前に気づける」ようにする。

### 9.4 公開ゲート（画像・名前・価格・店舗の一致保証）

「公開」into `approved` の必須条件。1つでも欠けたら公開不可:

1. 有効画像1枚以上 かつ その画像が `image_verified=true`
2. 既定価格が入力済み かつ `price_source_url` あり
3. shop_id・area_id が整合（shop.area_id == food.area_id、food_locations も同様）
4. `source_url` が公式ドメイン
5. `last_checked_at` が7日以内（公開時点の鮮度保証）
6. 重複候補キューに未処理ペアが残っていない

### 9.5 一覧共通表示

管理一覧の各行: サムネ / 名前 / 店舗 / 価格 / コレクションチップ / ステータス / **最終確認日**（30日超は琥珀色）/ 公式参照URLアイコン（新規タブ）。

## 10. 重複を防ぐ方法（ポリシーまとめ）

| ケース | 扱い | 担保 |
|---|---|---|
| 同名・同店舗 | 登録不可 | DB `unique(shop_id, normalized_name)` |
| 同商品・別店舗 | food 1件 + `food_locations` 追加 | 検出①→マージ、登録フォームの類似警告 |
| 価格違い・カップ付き・サイズ違い | food 1件 + `food_variants` | 検出②→variant化アクション |
| 表記揺れ（２５ｔｈ/25th、〜/~、スペース） | normalized_name 正規化強化 + 検出③ | 正規化関数にNFKC・長音・記号除去を追加 |
| 季節再販（2025夏→2026夏の同名商品） | 別foodとして登録可（collection_idが異なる）。`seasonal_version` に年を記録 | 検出③で候補提示→「別商品」でdismiss |
| 表示面 | 全一覧・全レールで `dedupeFoodsByCanonical` を通す。ホームはさらに §5.2 のセクション間排除 | 受け入れ条件で検査 |
